## Policy structure

Our policies are defined in JSON, with these three properties:

* `condition` identifies the circumstances under which the policy applies (such as signing with a specific wallet)
* `consensus` determines which user or users may take an action (for example, a given user ID)
* `effect` dictates if the activity should be allowed or denied based upon the evaluation of the `consensus` and `condition` fields

`consensus` and `condition` are ergonomic expressions written in the Turnkey [policy language](/concepts/policies/language) that must evaluate to a boolean. These fields can be used separately or together.

```json title="Allow a single user to send transactions to a single address"
{
  "effect": "EFFECT_ALLOW",
  "consensus": "approvers.any(user, user.id == '4b894565-fa11-42fc-b813-5bf4ea3d53f9')",
  "condition": "eth.tx.to == '<ALLOWED_ADDRESS>'"
}
```

<Tip>
Almost all actions on Turnkey are implicitly denied by default. You should design policies that enable those actions required by your integration.
</Tip>

## Policy evaluation

All policies defined within an Organization are evaluated on each request.

Written out:

<Steps>
  <Step>
    If a [quorum of root users](/concepts/users/root-quorum) takes the action, the final outcome is
    `OUTCOME_ALLOW`.
  </Step>
  <Step>
    Else if any applicable policy has `EFFECT_DENY`, the final outcome is `OUTCOME_DENY`. This is also referred to as _explicit deny_. In cases of conflicts, `EFFECT_DENY` always wins.
  </Step>
  <Step>
    Else if at least one applicable policy has `EFFECT_ALLOW`, then the final
    outcome is `OUTCOME_ALLOW`.
  </Step>
  <Step>
    Else the final outcome is `OUTCOME_DENY`. This is also referred to as
    _implicit deny_.
  </Step>
</Steps>

Almost all actions on Turnkey are implicitly denied by default. There are a few exceptions:

- The [quorum of root users](/concepts/users/root-quorum) bypasses all policies.
- All users have implicit GET (read) permissions in their own Organization and any associated Sub-Organizations.
- All users have implicit permission to change their own credentials, unless a policy explicitly allows or denies those actions.
- All users have implicit permission to approve an activity if the users are included in consensus. For example, a user specified as part of the consensus required to approve a `SIGN_TRANSACTION` activity does not need separate, explicit permission to sign transactions.
