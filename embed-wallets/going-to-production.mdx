## Security checklist

- [ ] Root org API keys are stored server-side only — never exposed to the browser
- [ ] Sub-org IDs are scoped per user — users cannot access each other's sub-orgs
- [ ] Recovery flows are protected by rate limiting and audit logging
- [ ] Policies are configured to restrict signing to expected transaction types
- [ ] Admin-initiated recovery requires explicit policy approval

- **Duplicate users**: Check if a sub-org already exists for an email before calling `createSubOrganization`
- **Failed sub-org creation**: Creation is atomic — if it fails, no partial state is left; retry safely
- **Passkey not available**: Fall back to email OTP and prompt the user to register a passkey after login
